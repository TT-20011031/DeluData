# 第一场演示·8 分钟分镜脚本

> 演示主线：**M1 编译实体页**（3 分钟）→ **M3 路由对比**（4.5 分钟）→ **收尾**（30 秒）。
>
> 演示前请按 `checklist.md` 完成 5 项自检。本脚本采用要点式，每步含「操作」「期望现象」「一句话价值」「技术亮点」四块。

---

## Step 0 · 准备（不计入 8 分钟）

**操作**

1. 浏览器打开 admin-frontend，使用 admin 账号登录
2. 进入 `知识库`（KnowledgeBasePage）
3. 新建文件夹 `产品手册`
4. 把 `docs/demo/part1/sample/` 下 3 份 `.md` 拖入文件夹
5. 等到右下角 toast 三次"上传成功"，确认每个文件状态都是 `已就绪`

> 上传需要等若干秒做切片入库，演示前请提前完成。

---

## Step 1 · M1 编译实体页（3 分钟）

### 1.1 切到 Wiki 视图（30 秒）

**操作**：知识库页右上角点 `Wiki 视图` 切换按钮。

**期望现象**：左侧 INDEX 面板出现，但内容为空（提示"暂无实体页"），右侧空白态显示"从左侧选择一个实体页"+ Wiki 路由健康度卡片（管理员可见）。

### 1.2 一键全量编译（1 分钟）

**操作**：点 INDEX 面板顶部的 **"全量编译"** 按钮。

**期望现象**：

- 按钮变 loading，耗时 30–60 秒
- toast 弹出：`新建 N / 更新 0，共编译 3 个文件`（N ≈ 6–10）
- 左侧 INDEX 自动出现按 domain 分组的实体页清单：
  - `product` 组：`deludata` / `knowledge-hub` / `wiki-first` 等
  - `module` 组：`rag` / `wiki` / `text-to-sql` / `chunk` / `entity-page` / `supervisor` / `worker` / `knowledge-router` 等

### 1.3 演示三联视图（1.5 分钟）

**操作**：点开实体页 `wiki`。

**期望现象**：右侧详情区呈现三联：

- **正文区**：markdown 渲染的实体页正文（约 300–500 字）
- **反向链接**：右侧栏列出"被 `deludata`、`knowledge-router`、`rag`、`entity-page` 等页引用"
- **出处证据**：底部"原文证据"列出 `chunk_id` 列表，悬停可看原始切片片段

> **一句话价值**：原本 3 份长 markdown 要靠关键词翻找，现在每个核心概念有了独立条目，自带"被谁引用 + 出处片段"。
>
> **技术亮点**：LLM 候选抽取 → slug 对齐去重 → 增量更新 / 新建 / 冲突标记 → 双向链接补全 → chunk 级出处溯源；编译过程不持事务，所有写入由 service 层在外层事务中原子提交。

---

## Step 2 · M3 路由对比（4.5 分钟）

切到对话页（保持空 Scope，不要勾任何 Wiki 域）。

### 2.1 第①问·"是什么"（1.5 分钟）

**操作**：在输入框输入：

> Wiki 是什么？

**期望现象**：

- 思维链区可见 `KnowledgeRouter → path=wiki, source=rule`
- 答案文本来自 [[wiki]] 实体页定义段
- citation 区显示 `📘 wiki`（实体页图标，非切片图标）

> **一句话价值**：常见的"是什么"问题在系统层面就被识别为概念问，**直接命中预编译实体页**，不再被淹没在长文里。
>
> **技术亮点**：命中 `router_keywords_wiki` 关键词（"是什么"），路由结果由规则直接给出，**0 LLM 调用**。

### 2.2 第②问·"原文摘录"（1.5 分钟）

**操作**：

> 原文摘录一下默认切片大小的描述

**期望现象**：

- 思维链区：`KnowledgeRouter → path=rag, source=rule`
- 答案是 `03-modules.md` 中"默认切片大小：**800 字**"那一句的原文片段
- citation 区显示 `📄 03-modules.md / 第 N 段`（切片图标）

> **一句话价值**：当用户要的就是原文出处时，系统不会绕弯解释概念，**直接命中切片做精准摘录**。
>
> **技术亮点**：命中 `router_keywords_rag` 关键词（"原文摘录"），同样 **0 LLM 调用**；与第①问形成完整的"两条路在检索前就分开"的对比。

### 2.3 第③问·"对比"（1.5 分钟）

**操作**：

> 对比一下 Supervisor 和 Worker

**期望现象**：

- 思维链区：`KnowledgeRouter → path=wiki, source=rule`（"对比"也是 wiki 关键词）
- 答案分两段，分别对齐 Supervisor 与 Worker 的职责
- citation 区同时显示 `📘 supervisor` 与 `📘 worker` 两个实体页

> **一句话价值**：对比类问题原本最难——RAG 切片之间没有显式语义关联；现在两个实体页天然可以并排合成回答。
>
> **技术亮点**：实体页层提供"概念 + 概念之间的双向链接"，Supervisor 的实体页本身就含 `[[worker]]` 出链，让"对比"类问题获得一致的概念视角。

---

## Step 3 · 收尾（30 秒）

一句话总结：

> **「文档没变、模型没变，但搜索和回答方式从『翻原文』变成了『先认概念再决定路径』」**——这是后续治理（健康巡检 / Wiki Gap 自动入队 / 配额纳管）能起作用的地基。

预告下一场：

> 第二场会演示三件治理能力：**Wiki 健康巡检**（孤儿/断链/冲突一键看到）、**Wiki Gap 自动入队**（问到没有的概念会自动派单后台编译）、**编译配额截断**（永远不会因为某次大量上传打爆工作区）。

---

## 演示者备忘

- 三个问题之间不要切换工作区或会话；同一个 session 比较直观
- 期望路由是否命中可在浏览器 DevTools `Network → /api/chat/...` 的响应里看 `knowledge_path` 字段
- 万一第②问没走 RAG（比如被 LLM 兜底走 wiki），改问 "请逐字摘录默认切片大小的具体数字" 几乎一定命中 `router_keywords_rag`
- 万一编译产出的实体页 < 6 个，多半是 LLM 抽取候选保守了——可以再补一句话题更聚焦的修改后再次编译；或者忽略不影响演示
