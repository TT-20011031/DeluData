# DeluData 产品总览

## 定义

**DeluData** 是一个面向企业的 AI 数据问答与知识中枢平台，基于 LangGraph 多智能体架构、多模态 RAG 与 Wiki-First 知识路由，把"原始文档堆"升级为"可问答、可治理、可追溯"的知识资产。

它的目标是解决一个具体痛点：当员工问"X 是什么"时，不应该被淹没在长达几十页的原始文档里——系统应当先理解问题类型，再决定走"原文摘录"还是"实体页解释"。

## 核心概念

DeluData 由四个相互协作的子系统组成：

- **多智能体编排** — 由 [[supervisor]] 统一调度，多个 [[worker]] 各司其职。
- **多模态 [[rag]]** — 支持 PDF / Word / Excel / Markdown / 纯文本，提供"语义切片 + 混合检索 + 重排序"。
- **[[wiki]] 知识中枢** — Karpathy LLM Wiki 模式，把核心实体编译成独立条目（`entity-page`），自带双向链接、出处溯源与修订历史。
- **[[knowledge-router]]** — 在检索前判定问题应走 Wiki / RAG / 混合（both）三条路径之一，实现"先认概念再决定路径"。

## 知识中枢（knowledge-hub）的工作方式

`knowledge-hub` 是 DeluData 对企业知识的统一抽象层。一个工作区内的所有原始文档经过摄取后，会同时存在于两个层：

1. **切片层（chunk 层）** — 由 [[rag]] 维护，用于"原文摘录"类问题。
2. **实体层（entity-page 层）** — 由 [[wiki]] 编译产生，用于"是什么 / 对比 / 概览"类问题。

两层共享同一份文档来源，但呈现方式完全不同。

## Wiki-First 路由的判定优先级

`wiki-first` 是 DeluData 的检索策略名称，由 [[knowledge-router]] 落地。它在 query 进入检索之前先做一次轻量分类，按以下优先级输出 `wiki / rag / both`：

1. **Scope 强制**：用户在前端勾了 Wiki 域或实体页 → 直接走 Wiki，零 LLM 调用。
2. **规则前置**：命中"是什么 / 对比 / 概览"等关键词 → Wiki；命中"原文 / 摘录 / 出处"等关键词 → RAG；零 LLM 调用。
3. **LLM 兜底**：规则不命中时，调用 fast 档位模型做一次结构化分类（输入 ≤ 80 token）。
4. **Fallback**：LLM 异常时回退到默认路径（默认 `both`）。

## 与传统 RAG 的关系

传统 RAG 把所有问题统一切片检索，导致两类典型问题被淹没：

- 概念性问题（"X 是什么"）只能拼凑切片，缺少完整的"定义 + 关系"视图。
- 概览性问题（"梳理下这个体系"）几乎无法回答，因为切片之间没有显式语义关联。

DeluData 把这两类问题分流到 [[wiki]] 实体页，把"原文摘录 / 出处定位"留给 [[rag]] 切片，从而**让两条路在检索前就分开**。

## 常见问题

**Q：DeluData 是替代 RAG 吗？**
A：不是。DeluData 同时保留 RAG 和 Wiki 两条检索路径，由 `knowledge-router` 决定每个问题走哪条；两层共享同一文档源。

**Q：实体页是手工维护的吗？**
A：不是。所有 `entity-page` 都由 [[wiki]] 的 WikiCompiler 在管理员触发"全量编译"时自动从原文档抽取，并自带 [[chunk]] 级出处溯源。

**Q：如果问到 Wiki 里没有的概念会怎样？**
A：系统会把这次"知识盲点"自动落库（Wiki Gap），后台编译完成后下次提问就能命中。
