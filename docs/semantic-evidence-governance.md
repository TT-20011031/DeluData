# 证据驱动的自动治理

本阶段把语义治理从固定置信度判断改为“采集证据—生成候选—人工决策—安全自动应用—反馈沉淀”的闭环。默认策略为 `observe_only=true`，治理运行会画像、评分并生成候选，但不会修改语义资产。

## 数据与隐私边界

- 画像仅保存行数、空值率、基数、唯一率、数字/日期范围、平均长度和敏感格式命中率。
- 字符串不保存最小值、最大值、TopK 或样例值。
- 小表精确聚合；大表使用最多 10,000 行的有界子查询。
- 单数据源并发为 1，默认单表查询超时 5 秒、最多 20 张表、整次运行最多 5 分钟。
- 超时和只读权限不足记为部分完成，不产生负向证据。

## 评分与自动应用

评分器按证据来源去重，每类只使用最强项：

`1 - ∏(1 - 可靠度 × 支持强度)`

冲突证据从支持结果中扣除。低于 0.65 的候选只留在证据库，不进入管理员主待办。

自动应用同时满足以下条件：

1. 得分不低于 0.98；
2. 至少两类独立证据；
3. 没有冲突证据；
4. 通过确定性校验；
5. 目标为 `management_mode=system` 且不是 `orphaned`；
6. 操作属于敏感标记、确定性失效停用等安全收敛白名单。

LLM 只能提出候选。人工资产、业务名、说明、同义词、公式和权限不会被自动修改。

## 上线步骤

1. 执行 `backend/migrations/add_semantic_evidence_governance.sql`。
2. 发布后端和主前端。
3. 保持观察模式，手动运行数轮治理，检查画像覆盖率、冲突证据和候选质量。
4. 处理高风险候选并观察 Shadow/回归等价率。
5. 确认自动变更错误数持续为 0 后，管理员在治理候选中心开放“安全自动治理”。

Schema Diff 成功应用后会自动触发治理运行；同一数据源的重复触发会合并。服务重启时，超过 30 分钟仍处于运行状态的任务会标记失败，可由管理员重新运行。

## 管理员操作

- “运行自动治理”：手动采集最新证据并生成候选。
- “观察模式”：只计算决策，不写语义资产。
- “接受当前修改”：允许先编辑 JSON Patch 再接受；资产随后固定为人工管理。
- “拒绝”：必须选择原因并填写说明，反馈长期有效。
- “批量接受/拒绝”：逐条事务处理，冲突项单独失败，不影响其他候选。
- “回滚自动变更”：仅适用于自动应用记录；若资产随后被人工修改，接口返回 `409`。
